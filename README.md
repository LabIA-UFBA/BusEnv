# TimesfmEnv — Multi-Agent Reinforcement Learning for Urban Bus Fleet Control

TimesfmEnv is a **multi-agent reinforcement learning (MARL) environment** designed to investigate the integration of time-series forecasting into urban bus fleet control. The environment combines real-world public transit operational data with predictive occupancy estimates, enabling reinforcement learning agents to make decisions based not only on the current system state but also on anticipated future demand.

The environment follows the [PettingZoo](https://pettingzoo.farama.org/) `ParallelEnv` API and is trained via [Ray RLlib](https://docs.ray.io/en/releases-1.8.0/rllib.html) or [MARLlib](https://github.com/Replicable-MARL/MARLlib).

---

## Highlights

- **Forecast-aware observations.** The environment can augment each agent's observation with occupancy predictions generated by external time-series forecasting models (e.g., TimesFM), allowing future demand information to be incorporated into the decision-making process.
- **Data-driven passenger demand.** Passenger boarding and alighting are modeled from historical operational records, where each `(route, stop)` maintains an independent passenger queue that evolves according to observed arrival rates instead of synthetic demand distributions.
- **Multi-agent coordination via headway awareness.** Each agent observes normalized gaps to its leading and following vehicles on the same route, encouraging coordinated behavior and reducing bus bunching.
- **Real-world transit network.** The environment operates on a real public transit network composed of historical routes and operational data, providing a realistic benchmark for MARL research.
- **Interactive replay visualization.** A browser-based replay viewer enables detailed inspection of simulated episodes through an interactive timeline, map visualization, and route analysis tools.

---

## Environment formulation

**Agents.** Each bus is an independent agent (`agent_0`, `agent_1`, …), assigned a fixed real route (an ordered sequence of GTFS stops) that it repeatedly traverses back and forth for the length of a simulated operational day (24h).

**Observation space** — `Box(12,)` per agent:

| # | Feature | Description |
|---|---|---|
| 0 | `time_of_day_norm` | Simulated time of day, normalized to [0, 1] |
| 1 | `occupancy_rate` | Current bus occupancy, fraction of capacity |
| 2 | `avg_travel_time_AB` | Normalized travel time to the next stop |
| 3 | `future_demand_at_B` | Historical boarding demand at the next stop |
| 4 | `uptime` | Normalized time since last maintenance |
| 5 | `maintenance_status` | 1.0 if operational, 0.0 otherwise |
| 6 | `curr_node_id` | Current stop (graph node index) |
| 7 | `next_node_id` | Next stop (graph node index) |
| 8 | `is_raining` | Weather flag (optional, data-driven) |
| 9 | `occ_risk_out` | Forecast risk of leaving the ideal occupancy band |
| 10 | `headway_leader_norm` | Signed, normalized time gap to the leading bus on the route |
| 11 | `headway_follower_norm` | Signed, normalized time gap to the following bus on the route |

**Action space** — `Discrete(3)`: `WAIT`, `MOVE` (advance to the next stop), `SERVICE_CENTER` (divert to a maintenance node).

**Reward.** The environment employs the **Forecast-Augmented Reward Function (FARF)**, which evaluates bus occupancy by combining the occupancy factor observed at the current stop with occupancy factors predicted for future stops.

The occupancy factor is computed using a Gaussian-shaped function centered at the desired occupancy level. Occupancy values within the target interval receive positive rewards, while values outside the interval are penalized. Overcrowding incurs an additional penalty to discourage excessive passenger loads.

When future occupancy predictions are available, the reward is computed as an exponentially weighted average of the current occupancy factor and the predicted occupancy factors for the next \(n\) stops. The weighting coefficients follow an exponential discount controlled by the parameter \(\gamma\), assigning greater importance to near-future predictions. Setting \(n = 0\) reduces the formulation to the baseline occupancy-only reward.

**Passenger demand model.** Each `(route, stop)` pair maintains an independent passenger queue that evolves according to historical passenger arrival rates. Between consecutive visits, the queue accumulates passengers based on observed arrival rates, while boarding is limited by the remaining vehicle capacity. Passenger alighting follows historical proportions estimated from operational data, resulting in realistic occupancy dynamics throughout each route.

## Data & demand pipeline

| Source | Content |
|---|---|
| `src/viz/graph_gtfs_fev_2024.gpickle` | Salvador GTFS network graph (Feb 2024): 2,871 stops with lat/lon, 4,526 edges with distance |
| `src/training_observation/real_routes.zip` | 668 real historical trip patterns (ordered stop sequences) |
| `src/training_observation/daily_may/` | Per-day travel-time / occupancy / uptime reference data |
| `src/training_observation/prediction/` | Per-day occupancy predictions|
| Raw AVL/APC-style parquet (`OD`, `Boarding`, `LTI`) | Per-visit boarding/alighting counts and timestamps, May 2024 (30 days) |

**`src/pipelines/generate_passenger_flow_stats.py`** aggregates the raw per-visit records into `stop_passenger_flow.pkl`: mean boardings, mean alighting fraction, and mean inter-visit interval, at a cascading granularity — `(route, stop, hour of day)` → `(route, stop)` → `(stop, hour of day)` → `(stop)` → a global fallback — so sparse combinations fall back to a broader, still-real estimate rather than an arbitrary default. Aggregation is a direct sum/count mean; no distribution-shape-sensitive outlier filtering is applied, since per-visit boarding/alighting counts are heavily zero-inflated and such filtering was found to systematically suppress real demand.

## Visualization

`src/viz/replay_export.py` + `src/viz/render_replay.py` turn a recorded episode (`record_replay=True`) into a self-contained HTML viewer: real OpenStreetMap basemap, a draggable timeline with step-by-step event navigation, live per-stop queue and per-bus occupancy indicators, editable route/stop labels, and PNG export for figures. `src/pipelines/generate_eval_replay.py` generates the replay logs, either from a random (untrained) policy or a trained checkpoint, enabling side-by-side before/after-training comparisons on a shared map scale.

See **[`src/viz/README.md`](src/viz/README.md)** for the exact commands.

## 🎯 Objective

The objective of this environment is to investigate whether incorporating **short-term occupancy forecasts** into the reinforcement learning state improves decision-making compared to relying only on the current occupancy.

To evaluate this hypothesis, agents learn a policy that aims to:

- Maintain bus occupancy close to a desired target level.
- Avoid both overcrowded and underutilized vehicles.
- Compare policies trained with and without occupancy predictions under identical conditions.

The environment enables a controlled comparison between a **baseline state representation**, which contains only the current occupancy, and an **augmented representation** that additionally includes occupancy forecasts generated by a foundation time-series forecasting model. This design isolates the effect of predictive information on reinforcement learning performance.

## 🛠 Training Setup

The environment integrates:

- **MARLlib** → Framework for MARL built on Ray RLlib.
- **Ray RLlib** → Distributed reinforcement learning.
- **PettingZoo** → Multi-agent environment API.
- **SuperSuit** → Wrappers for preprocessing.
- **Gymnasium** → Standard API.

**Configuration:**
- Each bus is an agent.
- Scenario based on real data (routes, stops, demand).
- Each episode ≈ one simulated operational day.
- PPO (Proximal Policy Optimization), independent or shared policies depending on the training script.

**Scaling:**
Supports **hundreds of agents in parallel**, leveraging Ray's distributed training.
